# WS53 适配进度与协议证据

当前已实现 BootROM 握手、LoaderBoot RAM 下载、串口回读、受限扇区替换和串口复位。
已实测候选02 Rust应用三扇区写入、整片回读和串口/物理复位启动，TIMER0输出经DSLogic与QEMU对照通过。
断电冷启动、本次应用恢复及完整Flasher集成仍未验收。
`ChipFamily::Ws53` 的普通 Flasher 创建仍拒绝；不能通过选择 WS63 绕过。

## 应用扇区计划与显式恢复（实验）

`ApplicationUpdate::new` 在任何设备I/O前校验全部原始/替换字节对、保护区、
范围、升序及不重叠；组合头必须最后写。`apply` 会先回读并比较全部计划区域，
最后一个区域的备份过期也不会先擦除前面的区域。每次D2前再次比较该区域，
完成后逐字节回读校验。失败保留区域索引、已验证数量及可能已修改Flash的状态，
不自动重试D2或复位到应用。

`recover` 只接受同一份已经验证的原始/拟写入计划，在重新进入LoaderBoot后
恢复计划内的原始区域，组合头仍最后写。它允许恢复擦除中断后丢失的保留字节；
普通替换接口会拒绝改变这些字节，不能拿普通接口冒充半擦除恢复。调用者必须
验证原始备份身份，检查计划外所有保护数据，并保存当前回读；不允许把损坏的
当前镜像重新当成原始备份。该层不解析镜像、不验证签名、不判断安全启动状态。

开发示例 `ws53_application` 消费由hisi-fwpkg生成的候选02扇区清单，固定清单、
LoaderBoot、原始整片备份哈希；其他镜像拒绝。它在写入前保存本次整片回读和
恢复扇区，校验启动/控制/校准区，保留同会话NV；写后三个扇区和整片回读都必须
一致。只在输出`VERIFIED_WAIT_BOOT`后收到标准输入`BOOT`才发送串口复位，
便于测试器先启动逻辑分析仪。文件持久化或协议失败均不发应用复位。

```sh
cargo build --locked -p hisiflash --example ws53_application
# check为离线模式，不打开串口；apply与recover会擦写已核对的三个扇区。
./target/debug/examples/ws53_application UART LOADER FULL_BACKUP PLAN_DIR NEW_OUTPUT check
```

主工程 `hil/ws53-flash-application.py` 编排新鲜安全状态证据、原厂AT基线、
BootROM入口、hisiflash写入/回读、DSLogic采集及启动结果。它生成可复查的
恢复命令，失败不自行重启。当前固定A板与候选02，尚不是普通`hisiflash flash`
命令的通用WS53支持。完整Flasher、芯片识别、其他板型和冷启动仍需独立验收。

协议测试覆盖整计划预检查、正文后组合头、整扇区擦除后保留字节恢复、后续区域
失败时保留已写状态、计划重叠/乱序/保护字段拒绝；既有芯片测试保持运行。

## 已实现并实测

`target::ws53::probe_bootrom` 对显式选定的 WS53 使用115200/8N1。
完整检查12字节 ACK 的长度、类型与 CRC；保留分片及 ACK 后的字节；
噪声缓存有界，支持取消、截止时间与断连错误，退出时恢复串口 timeout。
ACK 无芯片身份字段，成功只能证明 SEBOOT 应答，不能自动识别 WS53。

开发用命令（不发送 LoaderBoot、擦写或复位命令）：

```sh
cargo build --locked -p hisiflash --example ws53_probe
./target/debug/examples/ws53_probe /dev/serial/by-id/指定设备
```

需独立安排板卡复位/进入下载模式，完成后再次复位退出。
不要与串口监视器或其他下载进程同时占用串口。

2026-10-24 A板：J-Link23121302/串口5CB7019921，实测收到
`ef be ad de 0c 00 e1 1e 5a 00 95 22`，CRC通过；退出后原厂AT恢复。
后续实测 LoaderBoot 完成 ACK 为 `ef be ad de 0c 00 e1 1e 5a a5 da c7`，
并输出 `loaderboot|===== load cmd loop =====`。首次回读前4KiB与AP0备份
完全一致，SHA256为`3d15032f1f5f8e6d3f1ecf3d5f07e30807e8819805ef0c0d2e32511b0a3bf0e3`。
每轮结束复位恢复原厂AT；尚未发送Flash擦写命令。

后续完整4MiB回读（16×256KiB）通过，SHA256为
`c144174e9352e89fd9d70da6641fdbbc8df7a9685a8207c614fc388e2b591e16`。
与前一天AP0备份相比仅最后16KiB NV区不同（3674字节，原因未归因），
启动、控制核及应用镜像完全一致。复位恢复AT，SWD600/600及单步通过。
该备份仅保存在硬件证据目录，不包含在仓库的公开测试夹具中。

`load_loaderboot`复用已核对的YMODEM发送器，但不发送D2；完成后要求
CRC正确的SEBOOT ACK。`read_flash`实现B4上传接收，检查长度、CRC、序号、
重复包、序号回绕、结束包和最终ACK；有界超时，失败不返回数据并要求重新连接。
当前限制为4MiB Flash中的4字节对齐偏移，每事务最多256KiB。
10项WS53协议测试含多组正常/错误输入，覆盖旧有握手测试以及新流程。

开发示例可选参数（仍不写Flash；生成下载包的步骤见主工程
`scripts/prepare-ws53-loader.py`，示例只接受下述固定SHA256）：

```sh
./target/debug/examples/ws53_probe 指定串口 root_loaderboot_sign.bin
# 下载LoaderBoot并从偏移0回读；最后参数可省略，默认4096字节
./target/debug/examples/ws53_probe 指定串口 root_loaderboot_sign.bin backup.bin 4194304
```

输出文件在全部回读完成前可能不完整；只有`READBACK_OK`、预期长度和哈希
均核对后才可作为备份。任何失败必须复位/重新连接，不能继续原协议会话。

## 受限写入与串口复位（2026-10-24，续）

`replace_application_sectors`目前只允许已核实MCU-mode-1布局中的整4KiB扇区，
单事务不超过256KiB：应用子区`0x5d000..0x270000`，或组合头首扇区`0x30000`。
应用头`0x5d000..0x5d300`、控制核字节及安全策略字段必须与备份相同；
组合头只允许正文长度/摘要变化。通用镜像解释/生成仍归属hisi-fwpkg。
调用者须保存完整原始备份、核实真实分区/映射并验证整个待启动镜像；该接口
不签名、不探测安全启动状态，不以可写范围代替镜像完整性检查。

流程为B4读回与已保存备份逐字节比较→D2限定范围擦除→YMODEM→完整SEBOOT
完成ACK→独立B4逐字节校验。D2不自动重发；`WriteFailure`区分校验/读备份/
擦除/写入/验证阶段，并从首次尝试D2串口写入起标记Flash可能已改变，失败后
不得自动复位进入应用。需重新进入BootROM、加载已核实LoaderBoot并恢复备份。

D2为24字节：映射地址LE32、文件长度LE32、擦除长度LE32、ordinary Flash
类型`00 ff`、CRC16LE。与B4不同，D2使用`0x400000+物理偏移`。
除了厂商Channel.h/packet.py，固定LoaderBoot机器码偏移0x12CC的擦除包装器
和0x1028的写入调用都减0x400000，再交给SFC；禁止沿用B4物理偏移直传。
从不请求全片擦除、OTP/eFuse、安全配置或永久保护写入。

`request_loader_reset`发送厂商0x87/参数0，仅声明命令已发送，调用者必须独立
观察启动结果。A板已通过LoaderBoot下载→87复位→原厂AT恢复，无补救J-Link
复位；进入BootROM时仍需板级复位。此证据不等于断电冷启动。

开发例程`ws53_rewrite_sector`只接受固定SHA256的A板原始全片备份/LoaderBoot，
仅原样写偏移0x60000的4KiB，写前保存恢复内容及当前扇区，完整回读4MiB后
比较全部非NV区；新版本另在同一次LoaderBoot会话中核对NV前后不变。
`recover`模式允许当前目标扇区已损坏，先保存其内容再恢复固定原始数据。
它不是任意地址/任意固件烧录入口。主工程`hil/ws53-sector-roundtrip.py`保存
准确恢复命令；错误时不复位到可能写坏的应用。

13项WS53协议测试（多组输入）及旧芯片回归通过；新增越界、保护字节变化、
过期备份、擦除拒绝、传输断连、最终ACK失败和回读不符测试。
真实Rust应用下载、故意中断后的恢复、Flash外设/QEMU对照和断电冷启动仍未验收。


## 状态约束会话与当前验收（2026-10-24，续）

新增实验库接口`Ws53Session<P: Port>`，按`Fresh → Rom → Loader →
RegionsVerified → FullVerified → ResetRequested`推进。`apply`/`recover`只允许
在Loader阶段执行；每区域回读通过仍不能复位，必须再用同会话预期镜像完成
整片4MiB逐字节比较。任何协议、传输、取消或校验失败均进入`Failed`，后续
设备I/O拒绝，需要重新进入BootROM、创建新会话后显式恢复。参数/阶段错误在
I/O前拒绝。它不替代调用方的设备识别、安全状态核实、镜像审查和持久化备份。

`reset_after_verify`只发送0x87；`into_monitor_port`仅在发送成功后交回同一个
串口句柄，不重新打开或清缓冲区，供调用方捕获早期启动日志。复位命令成功不
代表应用运行或断电冷启动成功。底层协议接口保留供既有开发夹具使用。

状态会话有合成协议测试覆盖apply/recover完整流程、最终读回不一致、断连、
取消、非法顺序、后续区域失败进度及启动字节保留。本次硬件验证使用此前保存的
`ws53_application`二进制，不能据此宣称新状态会话已经真机验证。

A板候选02当前Flash证据：三个4KiB扇区（0x5d000、0x5e000、最后0x30000），
全片读回一致，控制核/启动/校准保留、NV与同会话写前一致。串口复位及物理SRST
均输出data/bss、WDT停止与IRQ53计数32；DSLogic D5采到32次交替边沿，间隔
9.987–10.013ms，匹配同ELF QEMU的10ms场景。此证据只覆盖具名基础能力，
其他外设须分别Flash重测；控制CPU仍保持复位，生产IPC尚未验收。

原厂单扇区原样重写不等于当前应用替换后的恢复。冷启动监听600秒未收到UART，
且未有物理断电确认，因此冷启动仍未验收。未执行安全配置/eFuse/永久保护写入。

## 实验 CLI：`hisiflash ws53`（2026-10-24）

普通`--chip ws53 flash`/`ChipFamily::create_flasher`仍未开放。新增独立入口
`hisiflash ws53 check|flash|recover`，只用于已核对的4MiB MCU-mode-1布局，
不会继承WS63的地址、自动选包、跳过校验或高速波特率配置。串口固定115200/8N1，
支持Ctrl-C，错误后不自动擦除重试或复位。新CLI尚未进行实板烧录验收。

图像格式与扇区规划调用hisi-fwpkg公开草稿PR #4的精确提交
`217447f82bcafa1bec0cad2f0170dc5056ea3c9b`，Cargo.lock固定同一来源。
不依赖本机绝对路径、Python生成器或SDK参与普通Cargo编译。该Git依赖是开发
阶段固定来源，尚不是新的crates.io版本；发布前需要对应依赖正式发布。

先构建并查看完整参数：

```sh
cargo build --locked --release -p hisiflash-cli
./target/release/hisiflash ws53 --help
```

先独立核对板卡、Flash布局、LoaderBoot来源和应用链接布局，保留完整原始备份
及其SHA-256。`--application`只接受已经验证入口`0x45d300`的原始Flash程序正文；
CLI拒绝ELF文件，但不能从raw bin证明链接地址、ABI或内存归属。RAM程序不能
因为改名为bin就用于烧录。`check`只做文件/布局/哈希检查，不枚举或打开串口：

```sh
hisiflash ws53 check \
  --loaderboot loaderboot-package.bin --loader-sha256 <已核实的LoaderBoot哈希> \
  --backup original-full.bin --backup-sha256 <独立保存的原始备份哈希> \
  --application application.bin --application-sha256 <已验证的Flash程序哈希> \
  --output new-check-directory
```

输出目录必须不存在。`plan.json`列出入口、完整输入哈希、每个原始/替换扇区
哈希以及核实范围，明确`security_read_by_cli=false`和
`elf_layout_validated_by_cli=false`。格式解析和哈希一致不证明签名有效。

真实写入需先通过独立只读流程确认目标板安全验证关闭，然后增加明确的串口、
USB桥序列号与该事实声明；不会读取或修改eFuse来满足条件：

```sh
hisiflash --port /dev/serial/by-id/<目标设备> ws53 flash \
  --usb-serial <目标串口桥序列号> --secure-boot-disabled \
  --loaderboot loaderboot-package.bin --loader-sha256 <LoaderBoot哈希> \
  --backup original-full.bin --backup-sha256 <原始备份哈希> \
  --application application.bin --application-sha256 <Flash程序哈希> \
  --output new-flash-directory --reset --expect 'WS53 FLASH PASS'
```

USB序列号标识串口桥，不是芯片ID。`ws53`命令显式选择芯片；共享ROM ACK不
作为识别证明。打开前重新核对串口枚举和USB序列号，随后10秒内需由板级流程
进入BootROM；CLI不主动切换DTR/RTS或发送AT复位。串口驱动打开行为仍须由
板级接线验证，不能直接假定其不影响电路。

设备访问前保存原始整片、应用、LoaderBoot、原始/替换扇区和
`recovery-command.json`；文件fsync，Linux另fsync目录及父目录，备份文件默认
仅当前用户可读写。读取当前整片后，普通写入要求除尾部16KiB可变NV外全部
匹配独立原始备份。恢复仅豁免本计划目标扇区的现场变化，计划外控制/启动/
校准数据仍须匹配。写后整片逐字节核对，NV保留同一会话写前内容。

`verified.json`只代表整片读回与`expected-full.bin`相同。指定`--reset`才在
全片校验后发送0x87；保持原串口句柄采集`boot-uart.bin`，`--expect`要求标记
恰好出现一次。没有指定标记只保存日志，不宣称应用成功。`--monitor-seconds`
为1–60秒。需要同步逻辑分析仪时加`--boot-on-stdin`，收到`FULL_VERIFY_OK`
后先确认分析仪READY，再在30秒内输入`BOOT`；超时、取消、错误输入均不发复位。

错误日志区分`failure.json`（未请求应用复位）、`reset-intent.json`（可能已
尝试发送）、`boot-failure.json`（写后验证通过，但复位/观察失败）。实际复位
命令发送成功也不代表应用正常或冷启动；任何路径均不会将冷启动标为通过。

恢复必须重新进入BootROM，以最初保留的备份/应用计划执行`ws53 recover`。
`recovery-command.json`包含准确argv和新的嵌套输出目录，不是shell字符串，
不要用shell拼接执行。它恢复本次计划的原始扇区，头部最后写，整片校验通过后

原厂启动标记需按原固件核对，不能把命令退出成功等同原厂运行验收。

## CLI 事务故障测试与结构化失败记录（2026-10-24，续）

CLI命令处理器新增字节级ROM/LoaderBoot主机测试。测试采用合成4MiB内容和
内存串口，验证实际命令处理器的文件持久化、YMODEM/CRC、B4、D2、全片校验、
串口复位和日志流程；它不枚举USB、不执行厂商或Rust固件，也不是QEMU/实板。
连接器注入只存在于私有函数的测试调用，生产CLI没有跳过设备身份检查的参数
或环境开关，仍在打开前检查USB序列号。

覆盖正常流程、第二次擦除后断连、重新连接恢复、写后保护区变化、部分复位
命令写入、重复启动标记、保存预期整片/验证报告失败，以及连接前取消。
模拟恢复会核对原始非NV整片恢复和同会话NV保持；它不能关闭实板恢复验收。

`failure.json`新增可供脚本直接读取的字段：

- `progress_scope=current_invocation`：进度和可能改写标志只针对本次调用，不能
  用false证明此前中断留下的Flash仍然完整。
- `flash_may_have_changed`、`verified_sectors`：保留已完成区域及首次D2尝试可能
  造成的修改；整片验证或文件保存失败也不会丢失已写状态。
- `failed_sector_index`、`failed_sector_offset`、`write_stage`：区域事务失败时
  给出索引/物理地址/阶段；整片或文件错误时为null，避免伪造失败扇区。
- `full_readback_verified`：独立说明全片比较是否完成；即使true，若验证报告
  无法持久化，也不会继续复位。

所有失败路径仍保留精确错误文字、复位状态及重新连接要求。测试不会自动修改
用户设备或把合成启动标记当成CPU运行证据。新CLI实板、断电冷启动、实际应用
恢复及各外设Flash/DSLogic对照继续独立待验收。

若`failure.json`或`boot-failure.json`本身无法写入，CLI仍在终端错误中保留原始
传输错误链和结构化进度，而不会用磁盘错误覆盖“已经部分改写”或“复位可能已
发送”的状态。测试同时注入第二次擦除断连/部分复位写入与失败日志写入失败，
确认不会输出成功报告，也不会进行额外复位。
